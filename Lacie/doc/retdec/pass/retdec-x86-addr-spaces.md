# retdec-x86-addr-spaces

`retdec-x86-addr-spaces` 是 RetDec 中专门针对 x86 架构地址空间（Segment Registers，如 FS 和 GS）的优化模块。它将对特定段寄存器的内存访问转换为更具语义的 intrinsic 函数调用。

## 功能概述

在 x86 架构（尤其是 Windows 和 Linux 的多线程实现）中，FS 和 GS 段寄存器经常被用来指向线程本地存储（TLS）、控制块（如 Windows 的 TIB/TEB）或其他特殊系统结构。普通的反编译可能会将这些访问识别为带偏移的内存读写。`retdec-x86-addr-spaces` 的目标是将这些底层的段相关访问“提升”为类似于 MSDN 定义的内部函数调用（如 `__readfsbyte`），从而提高代码的可读性，并使分析者一眼就能看出代码正在访问某种特殊的系统结构。

## 算法流程

该模块主要通过模式匹配和指令替换来实现：

1.  **架构过滤**：
    -   首先确认当前处理的是否为 x86 架构。如果不是，该模块不执行任何操作。

2.  **指令识别**：
    -   遍历函数中的指令，寻找 `LoadInst` 和 `StoreInst`。
    -   检查这些指令所使用的指针地址空间。在 LLVM 中，x86 的段地址空间通常被赋予特定的数值标识。

3.  **模式匹配与转换**：
    -   **Load 指令转换（`optimizeLoad`）**：
        -   识别对 FS 或 GS 段的 `load` 操作。
        -   根据加载数据的大小（Byte, Word, Dword, Qword），选择对应的 intrinsic 函数（如 `__readfsbyte`, `__readgsdword` 等）。
        -   创建该函数的调用（`CallInst`），并用其结果替换掉原本的 `load` 指令。
    -   **Store 指令转换（`optimizeStore`）**：
        -   识别对 FS 或 GS 段的 `store` 操作。
        -   根据存储数据的大小，选择对应的写入 intrinsic 函数（如 `__writefsbyte`, `__writegsqword` 等）。
        -   创建一个带有偏移量和数据的 `CallInst`，并删除原本的 `store` 指令。

4.  **影子函数创建**：
    -   如果模块中尚未定义这些 intrinsic 函数，该模块会自动创建符合 MSDN 规范的外部函数声明（External Linkage）。

## 总结

`retdec-x86-addr-spaces` 是一个典型的语义提升优化。它通过识别 x86 架构特有的段寄存器寻址模式，并将其还原为标准库级别的函数调用。这不仅让生成的代码更贴近人类编写的系统级 C 代码，还为后续识别操作系统特定结构（如线程局部变量或异常处理链）奠定了基础。

在 x86 架构中，**FS** 和 **GS** 被称为**段寄存器（Segment Registers）**。虽然名字听起来很古老，但在现代操作系统（如 Linux 和 Windows）中，它们扮演着极其关键的“导航员”角色。

为了让你的 PhD 研究更接地气，你可以把它们想象成指向**“系统机密数据库”**的专用指针。

---

## 1. 它们是什么“段”？

在早期的 16 位时代，段寄存器（CS, DS, SS, ES）用来突破 64KB 内存限制。但在现在的 32 位和 64 位保护模式下，它们的意义变了：

* **FS (Frame Segment)**：
* **Windows (x86)**：最著名的用途是指向 **TEB（线程环境块）**。通过 `FS:[0]`，程序可以找到当前线程的异常处理链（SEH）。
* **Linux**：常用于指向线程局部存储（TLS）。


* **GS (Global Segment)**：
* **Linux (x86)**：主要用于存放 **Stack Canary（栈保护值）**。这就是为什么你在 IR 中看到读取 `GS:[0x14]`。
* **Windows (x64)**：在 64 位 Windows 下，GS 取代了 FS 的位置，用来指向 TEB。



---

## 2. 为什么要专门识别它们的 `load`？

普通的 `load` 指令通常访问的是全局变量或栈上的数据（如你的 `func_array`）。但对 FS/GS 的 `load` 具有特殊的**语义价值**：

1. **身份识别**：如果代码执行 `load GS:[0x0]`，它可能是在获取当前线程的 ID 或某种系统句柄。
2. **安全防御**：正如你看到的 `__readgsdword(20)`，它专门从系统受保护的区域读取一个随机数（Canary），用来检测缓冲区溢出。
3. **反调试/反分析**：很多恶意软件或加壳工具会访问 `FS:[0x30]`（Windows 下的 PEB）来检查自己是否正在被调试器（如 OllyDbg/x64dbg）跟踪。

---

## 3. 在你的 IR 中如何体现？

RetDec 识别这些段操作的逻辑非常巧妙。在 LLVM IR 中，它使用 **AddrSpace（地址空间）** 来标记它们：

* **地址空间 256**  对应 **GS**
* **地址空间 257**  对应 **FS**

当你看到类似 `%3 = load i32, i32 addrspace(256)* ...` 时，`retdec-x86-addr-spaces` 这个 Pass 就会跳出来说：“嘿，这不仅仅是一个内存读取，这是一个对系统 GS 段的访问！” 然后把它提升为 `@__readgsdword`。
