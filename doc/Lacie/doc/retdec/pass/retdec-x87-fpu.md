# retdec-x87-fpu

`retdec-x87-fpu` 是 RetDec 中用于分析 x86 架构 x87 浮点单元（FPU）寄存器栈操作的 LLVM Pass。它通过复杂的约束求解，将相对于栈顶（TOP）的操作还原为具体的 FPU 寄存器访问。

## 功能概述

x87 FPU 使用一个环形寄存器栈（ST(0) 到 ST(7)），其指令（如 `fld`, `faddp`）的操作数通常是相对于当前栈顶指针（TOP）的偏移。在反编译出的 LLVM IR 中，这些操作最初可能表现为对全局 FPU 栈和 TOP 寄存器的读写。`retdec-x87-fpu` 的目标是分析每个基本块和函数执行后的 TOP 指针变化，推断出 ST(i) 偏移量所对应的实际寄存器编号，并将复杂的栈操作简化为普通的浮点指令映射。

## 算法流程

该 Pass 引入了矩阵方程求解等数学手段来处理不确定的栈状态：

1.  **元数据初始化（`FunctionAnalyzeMetadata`）**：
    -   为每个函数建立分析元数据。
    -   识别函数中控制 FPU 栈顶的全局变量（如 `top`）。
    -   定义基本块的入口状态（`inIndex`）和出口状态（`outIndex`）。

2.  **构建方程系统（addEquation）**：
    -   遍历函数中的指令，记录 FPU 指令如何改变 TOP 指针（如 `push` 导致 `TOP--`, `pop` 导致 `TOP++`）。
    -   建立跨越基本块（Basic Blocks）的流方程：`BB_out = BB_in + Delta`。
    -   对于控制流的分支和合并点，建立等式约束。

3.  **线性系统求解（`augmentedRank`）**：
    -   利用 `Eigen` 线性代数库构建矩阵方程组。
    -   通过分析矩阵的秩（Rank）和增广矩阵，确定系统的可解性。
    -   如果解是唯一的，则可以推断出每个位置的 TOP 指针绝对值。

4.  **指令分析与模拟（`analyzeInstruction`）**：
    -   在已知 TOP 绝对值的情况下，分析具体的 FPU 指令（利用 `capstone2llvmir` 提供的语义）。
    -   计算操作数对应的 `ST(i)` 到实际硬件寄存器编号的映射关系。

5.  **指令优化与替换（`optimizeAnalyzedFpuInstruction`）**：
    -   将原本复杂的“通过 TOP 查找物理寄存器并加载”的指令序列，替换为直接访问具体浮点寄存器的简单 LLVM 指令。
    -   清理不再需要的 TOP 修改指令和中间临时变量。

## 相关文件

## 总结

`retdec-x87-fpu` 是 RetDec 面对 x86 复杂架构特性时所展现的深度分析能力体现。它不仅依靠简单的启发式，还结合了严密的数学建模来解决 FPU 栈偏移的不确定性问题。这一过程将底层奇特的栈寻址模式还原为逻辑一致的寄存器数据流，极大地提升了涉及复杂浮点运算（如 3D 图形、科学计算）的反编译精度。

对于一个正在研究反编译器架构的 PhD 学生来说，你可以把 `retdec-x87-fpu` 看作是一个**“语义脱壳机”**。如果这个 Pass 不运行，你得到的代码将几乎无法阅读，甚至无法进行有效的数据流分析。

以下是深度解析为什么它能“保护”而不是“破坏”语义：

---

## 1. 消除“指针式”的寄存器寻址

x87 原始的 LLVM IR 非常丑陋，它把 8 个浮点寄存器模拟成一个数组 `fpu_stack[8]`，并用一个全局变量 `top` 来索引。

* **没有这个 Pass 时**：执行 `fadd` 变成了 `%val = load fpu_stack[top]`。在 LLVM 看来，这是一次**内存访问**。
* **有了这个 Pass 后**：它算出此时的 `top` 是 0，直接把指令改成 `%val = load ST0`。在 LLVM 看来，这是一次**寄存器访问**。

**结论**：它把原本模糊的“间接寻址”转换成了明确的“直接引用”，这让后续的分析工具（比如你的 **Pinpoint**）能像处理 `eax` 一样清晰地处理浮点数。

---

## 2. 它是如何防止“算错”的？

你担心的“破坏语义”通常指：如果它算错了 `top` 的值，会不会把 `ST(1)` 误认为是 `ST(2)`？

RetDec 使用了极其保守的**矩阵求秩算法**：

* **不确定，不转换**：如果方程组有多个解（说明代码逻辑在静态下确实不确定），这个 Pass 会选择**放弃优化**，保留原始的栈操作代码。
* **只有唯一解才动作**：只有当数学上证明该位置的 `top` 值百分之百确定时，它才会进行指令替换。

---

## 3. 它会干扰你的间接调用（Indirect Call）吗？

**完全不会。** * **架构隔离**：x86 架构中，间接跳转（`call eax`）使用的是通用寄存器，而这个 Pass 处理的是专门的浮点寄存器栈。两者在硬件层面就是分离开的。

* **数据流提纯**：如果你的 `httpd` 固件中有一段逻辑是“根据某个浮点运算的结果来计算跳转地址”（虽然罕见但存在），这个 Pass 把混乱的栈操作理顺后，反而能帮助你的 **Scholar** 智能体更轻松地回溯出那个跳转地址的来源。

---

## 4. 总结：它在语义提升链条中的位置

| 状态 | 表现形式 | 语义清晰度 |
| --- | --- | --- |
| **原始汇编** | `fld`, `faddp st(1), st(0)` | 极低（依赖运行时栈顶指针） |
| **Pass 运行前** | `load fpu_stack[top]`, `top--` | 低（充满干扰指令，难以追踪数据流） |
| **Pass 运行后** | `fadd ST0, ST1` | **高（变成了标准的数据依赖关系）** |
